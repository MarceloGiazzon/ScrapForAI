## The problem (finding A3/A4, confirmed on 2026-11-02)

- 7 ledger items cite ScrapForAI **job ids** as proof: `REG-215, REG-216, REG-217, REG-218, REG-223, WMS-9, WMS-12` — 15 distinct ids in total. Evidence expired after 4 hours, and a job id cannot be re-run, so each of those is "a claim, not a proof" by the ledger's own rule.
- `guard.kind: live` and `manual` are only checked for *path existence*; nothing ever executes them.

## What ScrapForAI already provides

| Need | Provided by |
|---|---|
| A proof that can be re-run | `PUT /v1/routines/:id` (versioned, immutable) and `scrapforai run <routine> --json` |
| Evidence that does not expire, and proves RED then GREEN | `scrapforai vault …` / `vault_add_from_run`, `vault_confirm_green` (`provenRed`, `firstGreen` pinned, with the sha256 of their signed manifests and the `buildId`) |
| A snapshot the NPDev gate can read **offline** | `scrapforai vault export --json` (deterministic: sorted ids, stable key order) |
| Re-execution when wanted | `scrapforai vault run <ITEM-ID> --json` (exit 0 passed / 1 failed / 2 could not run) |
| Third-party verifiable evidence | `scrapforai evidence export <jobId> --out x.zip`, `scrapforai evidence verify <folder> --expected-key-id <id>`, `scrapforai evidence chain` |
| A stable contract | `--json` output carries `cliSchema: 1`; the JSON Schema is `schema/cli.output.json` (regenerated by `npm run build`) |

## Proposal for the ledger

### 1. New guard kind

```yaml
guard:
  kind: routine
  ref: scrapforai:REG-215        # the id of a regression-vault item; same id as the ledger item when possible
  maxAgeDays: 30                  # optional; freshness alert threshold (default 30)
```

An item gets `ledgerRef: npdev:REG-215` on the ScrapForAI side, so the link is bidirectional.

### 2. Resolution in `check-done-item-guards.py`, three levels

1. **Offline (default in the gate; needs no browser and no ScrapForAI process).** The repo keeps a committed export, `ledger/scrapforai-vault.json`, produced by `scrapforai vault export --json` (use `.result` of the output, or `GET /v1/vault/export`). The guard resolves when the item exists there and:
   - `provenRed` is not null **or** `redNotCapturedReason` is non-empty (mirrors the ledger's own legacy policy);
   - `firstGreen` is not null (the fix was confirmed by a real run);
   - `provenRed.manifestSha256` / `firstGreen.manifestSha256` are 64-hex strings.
2. **Freshness (alert, not an error).** If `lastRun.status != passed` or `lastRun.at` is older than `maxAgeDays`, print a warning. A gate should not fail because nobody re-ran a test this month.
3. **Execution (`--execute`, opt-in, e.g. nightly CI or before a release).** Run `scrapforai vault run <ITEM-ID> --json`; require exit code 0. Exit 2 (infrastructure) is reported as "could not verify", not as "bug is back".

`kind: live` and `manual` keep their current meaning. The point is to give new and migrated items a guard that is a proof instead of a sentence.

### 3. Policy file

No change to the coverage ratchet. Items migrated in T2.5 stay `DONE`; their guard goes from `manual`/none to `routine`. Remove them from `legacy.ids` only if they were there (and lower `frozenCount` in the same commit, as the ledger README requires).

### 4. What the gate must NOT do

- Do not treat a valid signature as proof the *test* is right: it proves integrity and origin only. Reviewing the routine (it is a JSON file in `ROUTINE_LIBRARY_DIR`, reviewable in a PR) is still the human's job.
- Do not pin a trust decision to the key shipped inside an export. Record the installation's `keyId` once in the NPDev repo (`scrapforai evidence chain` prints it, as does `GET /v1/evidence/public-key`) and pass it as `--expected-key-id`.
- Do not depend on `lastRun.jobId` being resolvable: it is ephemeral unless pinned. `provenRed` / `firstGreen` are pinned and are the durable references.

### 5. Suggested wiring

```
# gate (offline, every pass)
python scripts/quality/check-done-item-guards.py

# nightly / pre-release (needs ScrapForAI running)
python scripts/quality/check-done-item-guards.py --execute
# refresh the committed snapshot (the REST body is the bare snapshot; the CLI wraps it in { cliSchema, command, exitCode, result }):
curl -s -H "Authorization: Bearer $SCRAPFORAI_API_KEY" http://127.0.0.1:3000/v1/vault/export > ledger/scrapforai-vault.json   # review the diff in the PR
```

## T2.5 — migrating the 7 expired proofs

Do this **per item**, honestly:

| Item | Option A — recreate as a proof | Option B — reclassify |
|---|---|---|
| `REG-215 REG-216 REG-217 REG-218 REG-223 WMS-9 WMS-12` | From the item's `detail`, write the routine, run it against a build that still has the bug (RED), then `vault_add_from_run`; after the fix, `vault_confirm_green`. Needs the app at a build where the original bug can still be reproduced, otherwise there is no honest RED. | Change `guard.kind` to `manual` and add a note: "ScrapForAI job ids cited here expired (4 h retention) and cannot be re-run." No false proof is better than a stale one. |

Where the bug is already fixed and cannot be reproduced any more, use Option A with `redNotCapturedReason: "legacy: found before the vault existed (job ids expired)"` and a GREEN from the current build; that is true and says exactly what is and is not proven.

Record the migration in the ledger itself (a `notes`/history entry per item), as the ledger requires. List the 15 job ids with:

```
grep -ohE "job_[A-Za-z0-9_-]{6,}" ledger/items/*.yml | sort -u
```
