# T5.2 - functional profile benchmark

Run on 2026-11-05 against the WmsOffice test instance (NPDev app, JWT mode, `localhost:8100`), through the CLI of a running
server: `npm run bench:profile -- reg-216 reg-218 wms-smoke-movimento --runs 10`. Each routine ran 10 times under `full` and 10
under `functional`, alternating the order so a warm cache does not always favour one profile. None of the three creates data.

| routine | runs per profile | full median (ms) | functional median (ms) | saved | step outcomes |
|---|---|---|---|---|---|
| reg-216 | 10 | 8387 | 9061 | -8.0% | identical |
| reg-218 | 10 | 6078 | 6715 | -10.5% | identical |
| wms-smoke-movimento | 10 | 9416 | 8749 | 7.1% | identical |

## Reading

- **Acceptance criterion met:** in all 60 runs the verdict and the step outcomes (passed/total, failed step index) were the same
  in both profiles. The functional profile changed no result.
- **No speed-up was measured.** The difference goes from -10.5% to +7.1% with no consistent sign, so it is noise. The target is
  on the same machine: images and fonts cost almost nothing, and the run time is dominated by the browser start-up and the
  application's own events. The profile does not pay off here; its value is on a target over a network with heavy images
  (to be measured there, not assumed). Screenshots and trace are off in `functional`, which saves disk, not time.
- Medians include the browser start-up (`durationMs` of the run); the CLI start-up is not counted.

## Not covered

One application (NPDev, local), three read-only routines, one machine. Not run against GeneXus or a remote target.

# Second benchmark (2026-11-10): heavy images over a link that is slow ON PURPOSE

The first run could not show a speed-up because its target was on the same machine. There is still no real remote target with heavy images here, so this
run **simulates** the link: `scripts/bench/heavy-site.mjs` serves a page with 30 images of about 352 KB each (random-pixel PNGs, incompressible, 10.3 MB in
all) and passes every response, the page and the XHR included, through ONE shared link with a latency and a bandwidth that the test sets
(`/__mode?latency=<ms>&mbps=<Mbit/s>`). **The link is a model, not a measurement of any real network**: the numbers below say what the profile does on a
link like that, and a real application, with its own images and its own events, must be measured the same way before the result is quoted for it.

Two library routines, each run 8 times per profile, alternating the order, through the project's own `npm run bench:profile` against a scratch server
(its own data directory and port; the API key still comes from `.env`):

- `bench-xhr`: open the page, type in a field, click a button that makes an XHR, wait for the answer. It never waits for the page to finish loading, so the
  images only get in the way by sharing the link with the XHR.
- `bench-idle`: open the page, `waitForLoadState networkidle`, check that the button is visible. The images are on its critical path.

| link | routine | full median (ms) | functional median (ms) | saved | step outcomes |
|---|---|---|---|---|---|
| none (the fixture on this machine) | bench-xhr | 1809 | 1725 | 4.6% | identical |
| none | bench-idle | 4477 | 3553 | 20.6% | identical |
| 60 ms latency, 40 Mbit/s shared | bench-xhr | 5536 | 4257 | 23.1% | identical |
| 60 ms latency, 40 Mbit/s shared | bench-idle | 5359 | 3747 | 30.1% | identical |
| 120 ms latency, 10 Mbit/s shared | bench-xhr | 10734 | 3697 | 65.6% | identical |
| 120 ms latency, 10 Mbit/s shared | bench-idle | 11387 | 3476 | 69.5% | identical |

## Reading

- **Acceptance still holds:** in all 96 runs (3 links x 2 routines x 2 profiles x 8) the verdict and the step outcomes were the same under both profiles.
- **The profile pays off exactly where the first report said it would: when images are heavy and the link is not free.** The saving grows as the link
  gets worse (4.6% and 20.6% with no link, 23% and 30% on a link like a decent office-to-server line, 66% and 70% on a poor one).
- **The server confirms the mechanism:** under `functional` the images never left the browser (answered with the 1x1 stand-in by the routing layer), so
  the fixture served the 30 images only for the `full` runs: 480 image requests (16 runs x 30, about 169 MB) in each condition, none for the 16
  `functional` runs of that condition.
- **How much depends on the routine, not only on the link.** `bench-idle` gains even on a free link (20.6%) because `networkidle` waits for the images;
  `bench-xhr` gains nothing there (4.6% is inside the noise of 8 runs) and gains a lot only when the images compete with the XHR for a slow link.
  A routine that waits with `waitForQuiet` (XHR/fetch only, the GeneXus pack's habit) sits between the two.
- The floor is about 3.5 s: the browser start-up and the page are in every median. Medians of 8 runs; the spread of a single condition was not
  recorded, so a difference of a few percent (the 4.6%) is not evidence.

## Still not covered

A real remote target; a real application's own images (a page with few or small images will gain little); GeneXus; more than one machine; the effect of
a CDN or HTTP/2 (the fixture is HTTP/1.1 on one origin, so the browser's six connections per host are part of what was measured).

## Reproduce

```
node scripts/bench/heavy-site.mjs                                   # the page, on :8190 (FIXTURE_PORT to change)
PORT=3099 HOST=127.0.0.1 SCRAPFORAI_DATA_DIR=<scratch>/data ARTIFACT_DIR=<scratch>/artifacts \
  ALLOWED_TARGET_ORIGINS=http://localhost:8190 SCHEDULER_ENABLED=false npx tsx src/server.ts   # a scratch server: nothing of your data is touched
# save a target profile `heavy-fixture` (baseUrl http://localhost:8190) and the two routines above on that server, then, per link:
curl "http://localhost:8190/__mode?latency=60&mbps=40"              # no query = no link
npm run bench:profile -- bench-xhr bench-idle --runs 8 --url http://localhost:3099
```
