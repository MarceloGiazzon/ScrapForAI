# T5.2 - functional profile benchmark

Run on 2026-11-05 against the WmsOffice test instance (NPDev app, JWT mode, `localhost:8100`), through the CLI of a running
server: `npm run bench:profile -- reg-216 reg-218 wms-smoke-movimento --runs 10`. Each routine ran 10 times under `full` and 10
under `functional`, alternating the order so a warm cache does not always favour one profile. None of the three creates data.

| routine | runs per profile | full median (ms) | functional median (ms) | saved | step outcomes |
|---|---|---|---|---|---|
| reg-216 | 10 | 8387 | 9061 | -8.0% | identical |
| reg-218 | 10 | 6078 | 6715 | -10.5% | identical |
| wms-smoke-movimento | 10 | 9416 | 8749 | 7.1% | identical |

## Reading

- **Acceptance criterion met:** in all 60 runs the verdict and the step outcomes (passed/total, failed step index) were the same
  in both profiles. The functional profile changed no result.
- **No speed-up was measured.** The difference goes from -10.5% to +7.1% with no consistent sign, so it is noise. The target is
  on the same machine: images and fonts cost almost nothing, and the run time is dominated by the browser start-up and the
  application's own events. The profile does not pay off here; its value is on a target over a network with heavy images
  (to be measured there, not assumed). Screenshots and trace are off in `functional`, which saves disk, not time.
- Medians include the browser start-up (`durationMs` of the run); the CLI start-up is not counted.

## Not covered

One application (NPDev, local), three read-only routines, one machine. Not run against GeneXus or a remote target.
