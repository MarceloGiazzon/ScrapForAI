Bóveda de regresión, firma e informes

Cómo un bug corregido se convierte en prueba permanente: la bóveda de regresión guarda la ejecución que falló (RED) y la primera que pasó (GREEN) como evidencia fijada, la evidencia se firma para poder verificarla en cualquier lugar, y un informe la convierte en un documento que se puede entregar.

Bóveda de regresión

Un bug corregido debe seguir corregido. La bóveda de regresión guarda cada bug corregido (o escenario difícil) en un archivo JSON, <ITEM-ID>.json, junto con la rutina que lo reproduce y dos evidencias fijadas: la ejecución que falló antes de la corrección y la primera que pasó después. Apunte REGRESSION_VAULT_DIR a un repositorio git para revisar los ítems en pull requests; el valor por defecto es <dataDir>/regression-vault.

Un ítem

CampoSignificado
idComo GX-12 o REG-209.
title, surface, tagsQué es y qué área de la aplicación toca.
typeBUG, SCENARIO o BOUNDARY.
severityLOW, MEDIUM, HIGH, P0, P1 o nulo.
statusACTIVE, QUARANTINED o RETIRED.
routine{ id, version }: una rutina de la biblioteca en una versión fija.
provenRedLa ejecución que falló: jobId, fecha, buildId y el sha256 de su manifiesto fijado. Nulo solo con un redNotCapturedReason.
firstGreenLa primera ejecución aprobada en un build con la corrección. Nulo hasta confirmarse; después nunca se sobrescribe.
lastRunLa ejecución más reciente del ítem, registrada por vault run.
ledgerRefVínculo opcional con un ledger externo, por ejemplo npdev:REG-209.

La evidencia no se escribe a mano. PUT /v1/vault/:id guarda solo la definición. provenRed, firstGreen y lastRun los completan únicamente los flujos de abajo, así que nadie puede declarar un RED o un GREEN que ninguna ejecución produjo.

De RED a GREEN

POST /v1/vault/add-from-run          (Authorization: Bearer <SCRAPFORAI_API_KEY>)
{ "id": "REG-209", "fromJobId": "job_abc123", "title": "El total ignora el descuento",
  "type": "BUG", "severity": "HIGH", "surface": "checkout", "ledgerRef": "npdev:REG-209" }

// ... el bug se corrige y se despliega ...

POST /v1/vault/REG-209/confirm-green  (Authorization: Bearer <SCRAPFORAI_API_KEY>)
{ "buildId": "2026.11.3-rc1" }
  1. add-from-run recibe una ejecución que falló, guarda sus pasos como rutina de la biblioteca (sin credenciales), fija la ejecución como provenRed y crea el ítem.
  2. confirm-green ejecuta la misma versión de la rutina. Solo si pasa la ejecución se fija como firstGreen. Si sigue en rojo, la respuesta es 409 y el ítem no cambia.
  3. POST /v1/vault/:id/run reverifica un ítem en cualquier momento y registra lastRun.

Los dos endpoints de captura exigen el token bearer; una sesión de la consola web no puede llamarlos. El buildId queda en los resultados y en las referencias de evidencia, para poder decir qué build estaba en rojo y cuál quedó en verde. Lo mismo está disponible desde la línea de comandos:

npm run cli -- vault list --status ACTIVE --tags checkout
npm run cli -- vault show REG-209
npm run cli -- vault run REG-209 --build-id 2026.11.3-rc1
npm run cli -- vault confirm-green REG-209 --build-id 2026.11.3-rc1
npm run cli -- vault export                    # instantánea determinista de toda la bóveda

Herramientas MCP: vault_list, vault_show, vault_add_from_run, vault_confirm_green y vault_run.

Ejecutar la bóveda, ordenada por impacto

Un ítem de suite puede traer ítems de la bóveda por filtro en lugar de nombrar rutinas. Con "order": "impact", los ítems con más probabilidad de romperse tras un cambio se ejecutan primero, así que una ejecución en rojo (y el failFast) aparece temprano.

POST /v1/suites
{
  "name": "pre-merge",
  "buildId": "2026.11.3-rc1",
  "items": [ { "vault": { "status": ["ACTIVE"], "tags": ["checkout"] } } ],
  "order": "impact",
  "impact": { "changedFiles": ["src/cart/total.js", "web/checkout/payment.html"] },
  "failFast": true
}

El orden es: superficie tocada (una entrada explícita en impact.surfaces, o un archivo cambiado que coincida con los globs de surfaces del perfil de destino) > falló en sus últimas 5 ejecuciones > severidad > id. Cada ejecución registra los motivos de su posición. POST /v1/vault/plan muestra el orden y los motivos sin ejecutar nada.

npm run cli -- vault run --impact --changed-files changed.txt --fail-fast --build-id 2026.11.3-rc1
git diff --name-only main | npm run cli -- vault run --impact --changed-files -

Usa el mismo veredicto y los mismos códigos de salida que cualquier suite: 0 verde, 1 rojo, 2 error de infraestructura.

La pantalla Vault

Con la consola web activada, Vault lista los ítems con estado, severidad, enlaces a la prueba RED y GREEN, última ejecución y un botón Run por ítem. Run by impact recibe una lista de archivos cambiados, muestra el orden y los motivos, ejecuta la bóveda como suite y abre su informe. La consola se autentica con una cookie de sesión, así que capturar evidencia (add-from-run, confirm-green), fijar y administrar credenciales siguen disponibles solo con el token bearer, desde la API, la CLI o MCP.

Evidencia firmada

Toda ejecución fijada tiene un manifest.json con el sha256 de cada archivo. Al fijar, ese manifiesto se firma con la clave Ed25519 de la instalación (<dataDir>/signing/ed25519.key, legible solo por su dueño). El keyId es el sha256 de la clave pública.

  • GET /v1/evidence/public-key devuelve la clave pública y su keyId.
  • La evidencia fijada antes de que existiera la firma figura como unsigned, no es confiable y no se puede exportar. Vuelva a fijarla desde una ejecución nueva.

La cadena

Cada manifiesto firmado lleva chain: { sequence, previousManifestSha256 }. Editar un manifiesto rompe el eslabón siguiente; quitar uno deja un hueco en la secuencia; quitar los más recientes lo detecta una marca de agua (pinned/chain.json).

GET /v1/evidence/chain            // eslabones, huecos, firmas
GET /v1/evidence/chain?deep=1     // además recalcula el hash de cada archivo fijado
npm run cli -- evidence chain --deep

Exportación y verificación offline

npm run cli -- evidence export job_abc123 --out REG-209-red.zip
# en cualquier máquina, sin servidor y sin configuración:
scrapforai evidence verify .\REG-209-red --expected-key-id <keyId>

GET /v1/runs/:jobId/export (solo ejecuciones fijadas) devuelve un .zip con los archivos de evidencia, el manifiesto firmado, public-key.pem y un README. Se rechaza (409) si la ejecución no está fijada, no tiene una firma válida de esta instalación, o si sus archivos ya no coinciden con el manifiesto. evidence verify acepta una carpeta descomprimida o un job id; sale con 0 cuando todo verifica y con 1 en caso contrario. El código de verificación no importa configuración del servidor a propósito, así que funciona donde estén los archivos.

Pase --expected-key-id con el id que obtuvo del dueño por otro canal. Sin eso, la clave dentro de la carpeta solo prueba que el paquete es coherente consigo mismo.

Qué prueba una firma

  • Prueba integridad y origen: esta instalación firmó exactamente estos archivos, y ninguno cambió desde entonces.
  • No prueba que el test fuera correcto, que la aplicación probada sea lo que dice ser, ni nada sobre una máquina cuya clave privada o directorio de datos completo esté comprometido.
  • Haga copia de seguridad de <dataDir>/signing/ y de pinned/ juntos. La evidencia fijada nunca se borra automáticamente (el tope es PINNED_EVIDENCE_MAX_MB; por encima, la fijación se rechaza con 409).

Informes

Un informe convierte una ejecución, o una suite completa, en un documento de homologación: aplicación, entorno, build, fecha, ejecutor, rutina y versión, veredicto, pasos con tiempos, captura de la falla, resumen de consola y red, aviso de teardown si la limpieza falló, y un pie con el keyId de la firma, el sha256 del manifiesto y la posición en la cadena (o un "no firmado / expirado" explícito).

GET /v1/runs/job_abc123/report?format=pdf&lang=es
GET /v1/suites/suite_xyz/report?format=html&lang=pt
npm run cli -- report job_abc123 --out informe.pdf --format pdf --lang es
npm run cli -- report suite_xyz --out suite.html --lang en
  • format es html (por defecto) o pdf; lang es en (por defecto), pt o es.
  • El HTML es un único archivo autocontenido con las capturas incrustadas, bajo una política de seguridad de contenido sin scripts. Todo lo que viene de la ejecución se escapa, así que la página probada no puede inyectarle nada.
  • El PDF lo imprime el mismo Chromium, con todas las solicitudes de red abortadas.
  • Un informe necesita que la evidencia de la ejecución aún exista. Fije lo que va a reportar. El informe de una suite se rechaza (409) mientras la suite sigue en curso.
