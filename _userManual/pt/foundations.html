Credenciais, rotinas e suítes

Os blocos do lado do servidor que transformam execuções avulsas em prova reutilizável e repetível: cofre de credenciais, perfis de alvo, rotinas versionadas, suítes, evidência fixada e um cliente de linha de comando.

Cofre de credenciais

Os segredos ficam cifrados no servidor (AES-256-GCM) e são referenciados por id. Quem chama, inclusive um modelo de IA, envia credentialSet: "gam-admin"; o servidor carrega os valores e os steps continuam usando valueFromCredential pelo nome do campo. Os valores são somente escrita: nenhuma API, log, resultado ou histórico os devolve.

PUT /v1/credentials/gam-admin        (Authorization: Bearer <SCRAPFORAI_API_KEY>)
{
  "boundOrigins": ["https://dev.example.com"],
  "values": { "loginUser": "...", "loginPassword": "..." },
  "tags": ["role:admin"]
}
POST /v1/explorations/run
{
  "targetProfile": "app-dev",
  "credentialSet": "gam-admin",
  "steps": [
    { "action": "goto", "url": "$targetUrl" },
    { "action": "fill", "selector": "#vUSER", "valueFromCredential": "loginUser" },
    { "action": "fill", "selector": "#vPASS", "valueFromCredential": "loginPassword" }
  ]
}
  • Vínculo por origem. Cada conjunto lista boundOrigins. Um fill de valor do cofre em outra origem falha com CredentialOriginMismatch, mesmo que essa origem esteja na allowlist.
  • Quem escreve. POST/PUT/DELETE /v1/credentials/:id exigem o bearer token; uma sessão do console web não basta. GET devolve só ids, origens, nomes de campos, tags e último uso.
  • Chave. SCRAPFORAI_VAULT_KEY (32 bytes, base64) ou um vault.key gerado no diretório de dados. Sem a chave o cofre não pode ser lido.
  • MCP. A ferramenta run_exploration não tem o campo credentials, então o modelo nunca escreve nem vê um segredo. list_credential_sets mostra o que existe.
  • Legado. A API REST ainda aceita credentials inline (obsoleto, registrado em log). Use ALLOW_INLINE_CREDENTIALS=false para exigir o cofre.

Perfis de alvo

Um perfil dá nome a uma aplicação e ambiente, fornece o targetUrl padrão e lista os conjuntos de credenciais que uma execução pode usar. Ele nunca amplia ALLOWED_TARGET_ORIGINS: um baseUrl fora dela é recusado.

PUT /v1/targets/app-dev
{
  "name": "My app (dev)",
  "environment": "dev",
  "baseUrl": "https://dev.example.com/app",
  "platform": "genexus",
  "credentialSets": ["gam-admin", "gam-readonly"],
  "flags": { "maxSessionsPerCredential": 1 }
}

Use com "targetProfile": "app-dev" numa execução. maxSessionsPerCredential (padrão 1) é quantas sessões simultâneas uma credencial pode ter.

Rotinas salvas

Uma rotina é dado, então pode ser guardada, versionada e revisada. Cada mudança é uma versão imutável (v1.json, v2.json); salvar conteúdo idêntico não cria nada. O sha256 de cada versão é conferido a cada leitura.

PUT /v1/routines/crud-sales
{ "title": "Sales CRUD", "targetProfile": "app-dev", "credentialSet": "gam-admin",
  "steps": [ { "id": "auth", "action": "include", "routineId": "login", "version": 1 },
             { "id": "open", "action": "click", "selector": "#menu-sales" } ],
  "teardown": [ { "id": "bye", "action": "goto", "url": "https://dev.example.com/app/logout" } ] }

PUT /v1/routines/crud-sales      { "fromJobId": "job_abc123" }      // save a run that worked
POST /v1/routines/crud-sales/run?version=2
  • Segredos são recusados. Um literal igual a um valor do cofre, ou com formato de chave de API, JWT ou token, é rejeitado ao salvar (422).
  • fromJobId salva os steps de uma execução que passou, enquanto a evidência ainda existe.
  • Status: draft, active, quarantined, retired. Mudá-lo é uma nova versão. As suítes rodam só active por padrão.
  • Aponte ROUTINE_LIBRARY_DIR para dentro de um repositório git para revisar rotinas em pull requests.

Include e teardown

{ "action": "include", "routineId": "login" } expande outra rotina salva no lugar. Os ids dos steps expandidos recebem o prefixo do id do include (auth.submit). Até 3 níveis; ciclos são recusados ao salvar; a rotina incluída deve ser do mesmo perfil de alvo e não estar aposentada. Sem version usa-se a versão atual, então fixe a versão para prova reproduzível. As versões realmente usadas ficam em result.includes.

teardown é uma lista de steps que sempre roda depois dos steps, passando ou falhando (como um finally): primeiro o teardown da própria rotina, depois os das rotinas incluídas, a última incluída primeiro. Falhas de teardown aparecem em result.teardown e teardownStatus; nunca mudam o status da execução nem substituem a falha de um step.

Suítes

Uma suíte roda várias rotinas salvas, multiplicadas por conjuntos de credenciais e perfis de alvo. Iniciar uma responde 202 na hora e ela roda em segundo plano.

POST /v1/suites                                  -> 202 { "suiteRunId": "suite_..." }
{
  "name": "nightly",
  "items": [ { "routineId": "crud-sales" }, { "routineId": "report-activity" } ],
  "variants": { "credentialSets": ["gam-admin", "gam-readonly"], "targetProfiles": ["app-dev", "app-qa"] },
  "failFast": false
}
GET /v1/suites/suite_...?wait=30                 // blocks up to 55 s until it ends
  • Cada execução tem uma variantKey legível, por exemplo crud-sales@v2/cred:gam-admin/target:app-qa. As versões das rotinas são fixadas quando a suíte começa.
  • Um só veredito: green (saída 0), red (1, uma execução falhou) ou infra-error (2, uma execução não pôde rodar, nada rodou ou foi cancelada).
  • Uma sessão por credencial. Execuções que dividem um conjunto de credenciais nunca se sobrepõem; uma execução direta que precisa de uma credencial ocupada recebe 409 CredentialInUse.
  • failFast para de iniciar execuções no primeiro vermelho; as demais ficam listadas como não executadas. POST /v1/suites/:id/cancel interrompe a suíte.
  • MAX_PARALLEL_JOBS é o pool compartilhado; INTERACTIVE_RESERVED_SLOTS (padrão 1) nunca vão para suítes.

Retenção e evidência fixada

A evidência expira após ARTIFACT_RETENTION_HOURS (4 h), a menos que a execução use options.retention: "standard" (STANDARD_RETENTION_DAYS, 30 dias). Para guardar a prova de vez, fixe-a:

POST /v1/runs/job_abc123/pin
{ "reason": "proof for REG-209", "ref": "npdev:REG-209" }

GET /v1/runs/job_abc123/manifest   // sha256 of every file, re-verified now

Fixar move a execução para um armazenamento que nunca é limpo (limitado por PINNED_EVIDENCE_MAX_MB; acima do limite vem 409 e nada é apagado), descarta o trace pesado salvo com keepTrace e recusa evidência cujo manifesto não confere mais com os arquivos. O manifesto prova que os arquivos não mudaram; não prova que o teste estava certo.

A linha de comando scrapforai

npm run cli -- run crud-sales --version 2 --json
npm run cli -- suite nightly.json
npm run cli -- routines list
npm run cli -- runs show job_abc123
npm run cli -- pin job_abc123 --reason "proof" --ref npdev:REG-209

A CLI fala com a API REST usando a chave do .env (nunca pela linha de comando). Códigos de saída: 0 passou, 1 um teste falhou, 2 qualquer outra coisa (API fora, argumentos inválidos, execução que não pôde rodar). Com --json imprime exatamente um objeto JSON no stdout, versionado por cliSchema; o progresso vai para o stderr.

{ "cliSchema": 1, "command": "run", "exitCode": 1,
  "result": { "jobId": "job_...", "status": "failed", "failedStepIndex": 2, "error": { "type": "StepExecutionError", "message": "..." } } }

Ferramentas MCP

Fluxo recomendado para um agente de IA: list_targets → inspect_dom → run_exploration → save_routine (com fromJobId) → depois run_routine ou run_suite + get_suite_result.

FerramentaFinalidade
list_credential_sets, list_targetsDescobrir o que o servidor oferece (nunca valores secretos).
inspect_dom, run_explorationExplorar uma página e executar steps.
list_routines, get_routine, save_routine, run_routineA biblioteca de rotinas.
run_suite, get_suite_resultIniciar uma suíte (retorna na hora) e esperá-la com waitSeconds.
get_runResumo (e opcionalmente o resultado completo) de uma execução passada.
