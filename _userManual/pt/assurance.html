Cofre de regressão, assinatura e relatórios

Como um bug corrigido vira prova permanente: o cofre de regressão guarda a execução que falhou (RED) e a primeira que passou (GREEN) como evidência fixada, a evidência é assinada para poder ser verificada em qualquer lugar, e um relatório a transforma num documento que você pode entregar.

Cofre de regressão

Um bug corrigido deve continuar corrigido. O cofre de regressão guarda cada bug corrigido (ou cenário difícil) num arquivo JSON, <ITEM-ID>.json, junto com a rotina que o reproduz e duas evidências fixadas: a execução que falhou antes da correção e a primeira que passou depois dela. Aponte REGRESSION_VAULT_DIR para dentro de um repositório git para revisar os itens em pull requests; o padrão é <dataDir>/regression-vault.

Um item

CampoSignificado
idComo GX-12 ou REG-209.
title, surface, tagsO que é e que área da aplicação toca.
typeBUG, SCENARIO ou BOUNDARY.
severityLOW, MEDIUM, HIGH, P0, P1 ou nulo.
statusACTIVE, QUARANTINED ou RETIRED.
routine{ id, version }: uma rotina da biblioteca numa versão fixa.
provenRedA execução que falhou: jobId, data, buildId e o sha256 do manifesto fixado. Nulo só com um redNotCapturedReason.
firstGreenA primeira execução aprovada num build com a correção. Nulo até ser confirmado; depois nunca é sobrescrito.
lastRunA execução mais recente do item, gravada por vault run.
ledgerRefVínculo opcional com um ledger externo, por exemplo npdev:REG-209.

Evidência não se digita. PUT /v1/vault/:id grava só a definição. provenRed, firstGreen e lastRun são preenchidos apenas pelos fluxos abaixo, então ninguém consegue declarar um RED ou um GREEN que nenhuma execução produziu.

De RED para GREEN

POST /v1/vault/add-from-run          (Authorization: Bearer <SCRAPFORAI_API_KEY>)
{ "id": "REG-209", "fromJobId": "job_abc123", "title": "Total ignora o desconto",
  "type": "BUG", "severity": "HIGH", "surface": "checkout", "ledgerRef": "npdev:REG-209" }

// ... o bug é corrigido e publicado ...

POST /v1/vault/REG-209/confirm-green  (Authorization: Bearer <SCRAPFORAI_API_KEY>)
{ "buildId": "2026.11.3-rc1" }
  1. add-from-run recebe uma execução que falhou, salva seus passos como rotina da biblioteca (sem credenciais), fixa a execução como provenRed e cria o item.
  2. confirm-green roda a mesma versão da rotina. Só se ela passar a execução é fixada como firstGreen. Se ainda estiver vermelha, a resposta é 409 e o item não muda.
  3. POST /v1/vault/:id/run reverifica um item a qualquer momento e grava lastRun.

Os dois endpoints de captura exigem o token bearer; uma sessão do console web não consegue chamá-los. O buildId fica nos resultados e nas referências de evidência, para dizer qual build estava vermelho e qual ficou verde. O mesmo está disponível na linha de comando:

npm run cli -- vault list --status ACTIVE --tags checkout
npm run cli -- vault show REG-209
npm run cli -- vault run REG-209 --build-id 2026.11.3-rc1
npm run cli -- vault confirm-green REG-209 --build-id 2026.11.3-rc1
npm run cli -- vault export                    # retrato determinístico do cofre inteiro

Ferramentas MCP: vault_list, vault_show, vault_add_from_run, vault_confirm_green e vault_run.

Rodando o cofre, ordenado por impacto

Um item de suíte pode puxar itens do cofre por filtro em vez de nomear rotinas. Com "order": "impact", os itens com mais chance de quebrar depois de uma mudança rodam primeiro, então uma execução vermelha (e o failFast) aparece cedo.

POST /v1/suites
{
  "name": "pre-merge",
  "buildId": "2026.11.3-rc1",
  "items": [ { "vault": { "status": ["ACTIVE"], "tags": ["checkout"] } } ],
  "order": "impact",
  "impact": { "changedFiles": ["src/cart/total.js", "web/checkout/payment.html"] },
  "failFast": true
}

A ordem é: superfície tocada (uma entrada explícita em impact.surfaces, ou um arquivo alterado que case com os globs de surfaces do perfil de alvo) > falhou nas últimas 5 execuções > severidade > id. Cada execução registra os motivos da sua posição. POST /v1/vault/plan mostra a ordem e os motivos sem executar nada.

npm run cli -- vault run --impact --changed-files changed.txt --fail-fast --build-id 2026.11.3-rc1
git diff --name-only main | npm run cli -- vault run --impact --changed-files -

Usa o mesmo veredito e os mesmos códigos de saída de qualquer suíte: 0 verde, 1 vermelho, 2 erro de infraestrutura.

A tela Vault

Com o console web ligado, Vault lista os itens com status, severidade, links para a prova RED e GREEN, última execução e um botão Run por item. Run by impact recebe uma lista de arquivos alterados, mostra a ordem e os motivos, roda o cofre como suíte e abre o relatório. O console autentica com cookie de sessão, então capturar evidência (add-from-run, confirm-green), fixar e gerenciar credenciais continuam disponíveis só com o token bearer, pela API, pela CLI ou pelo MCP.

Evidência assinada

Toda execução fixada tem um manifest.json com o sha256 de cada arquivo. No momento da fixação esse manifesto é assinado com a chave Ed25519 da instalação (<dataDir>/signing/ed25519.key, legível só pelo dono). O keyId é o sha256 da chave pública.

  • GET /v1/evidence/public-key devolve a chave pública e seu keyId.
  • Evidência fixada antes de a assinatura existir aparece como unsigned, não é confiável e não pode ser exportada. Fixe de novo a partir de uma nova execução.

A cadeia

Cada manifesto assinado carrega chain: { sequence, previousManifestSha256 }. Editar um manifesto quebra o elo seguinte; remover um deixa um buraco na sequência; remover os mais recentes é detectado por uma marca d'água (pinned/chain.json).

GET /v1/evidence/chain            // elos, buracos, assinaturas
GET /v1/evidence/chain?deep=1     // também recalcula o hash de cada arquivo fixado
npm run cli -- evidence chain --deep

Exportação e verificação offline

npm run cli -- evidence export job_abc123 --out REG-209-red.zip
# em qualquer máquina, sem servidor e sem configuração:
scrapforai evidence verify .\REG-209-red --expected-key-id <keyId>

GET /v1/runs/:jobId/export (só execuções fixadas) devolve um .zip com os arquivos de evidência, o manifesto assinado, public-key.pem e um README. É recusado (409) se a execução não estiver fixada, não tiver assinatura válida desta instalação, ou se os arquivos não baterem mais com o manifesto. evidence verify aceita uma pasta descompactada ou um job id; sai com 0 quando tudo confere e com 1 caso contrário. O código de verificação não importa configuração do servidor de propósito, então funciona onde os arquivos estiverem.

Passe --expected-key-id com o id que você obteve do dono por outro canal. Sem isso, a chave dentro da pasta só prova que o pacote é consistente consigo mesmo.

O que uma assinatura prova

  • Prova integridade e origem: esta instalação assinou exatamente estes arquivos, e nenhum mudou desde então.
  • Não prova que o teste estava correto, que a aplicação testada é o que diz ser, nem nada sobre uma máquina cuja chave privada ou diretório de dados inteiro esteja comprometido.
  • Faça backup de <dataDir>/signing/ e de pinned/ juntos. A evidência fixada nunca é apagada automaticamente (o limite é PINNED_EVIDENCE_MAX_MB; acima dele, a fixação é recusada com 409).

Relatórios

Um relatório transforma uma execução, ou uma suíte inteira, num documento de homologação: aplicação, ambiente, build, data, executor, rotina e versão, veredito, passos com tempos, captura da falha, resumo de console e rede, aviso de teardown se a limpeza falhou, e um rodapé com o keyId da assinatura, o sha256 do manifesto e a posição na cadeia (ou um "não assinado / expirado" explícito).

GET /v1/runs/job_abc123/report?format=pdf&lang=pt
GET /v1/suites/suite_xyz/report?format=html&lang=es
npm run cli -- report job_abc123 --out relatorio.pdf --format pdf --lang pt
npm run cli -- report suite_xyz --out suite.html --lang es
  • format é html (padrão) ou pdf; lang é en (padrão), pt ou es.
  • O HTML é um único arquivo autocontido com as capturas embutidas, sob uma política de segurança de conteúdo sem scripts. Tudo o que vem da execução é escapado, então a página testada não consegue injetar nada nele.
  • O PDF é impresso pelo mesmo Chromium, com todas as requisições de rede abortadas.
  • Um relatório precisa que a evidência da execução ainda exista. Fixe o que você vai reportar. O relatório de uma suíte é recusado (409) enquanto ela ainda roda.
