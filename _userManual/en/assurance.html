Regression vault, signed evidence & reports

How a fixed bug becomes permanent proof: the regression vault keeps the failing run (RED) and the first passing run (GREEN) as pinned evidence, the evidence is signed so it can be verified anywhere, and a report turns it into a document you can hand over.

Regression vault

A bug that was fixed should stay fixed. The regression vault stores each fixed bug (or hard scenario) as one JSON file, <ITEM-ID>.json, together with the routine that reproduces it and two pieces of pinned evidence: the run that failed before the fix and the first run that passed after it. Set REGRESSION_VAULT_DIR inside a git repository to review items in pull requests; the default is <dataDir>/regression-vault.

An item

FieldMeaning
idLike GX-12 or REG-209.
title, surface, tagsWhat it is and which area of the application it touches.
typeBUG, SCENARIO or BOUNDARY.
severityLOW, MEDIUM, HIGH, P0, P1 or null.
statusACTIVE, QUARANTINED or RETIRED.
routine{ id, version }: a library routine at a pinned version.
provenRedThe failing run: jobId, date, buildId and the sha256 of its pinned manifest. Null only with a redNotCapturedReason.
firstGreenThe first passing run on a build with the fix. Null until confirmed; never overwritten afterwards.
lastRunThe most recent run of the item, recorded by vault run.
ledgerRefOptional link to an external ledger, e.g. npdev:REG-209.

Evidence cannot be typed in. PUT /v1/vault/:id writes only the definition. provenRed, firstGreen and lastRun are set only by the flows below, so nobody can claim a RED or a GREEN that no run produced.

RED to GREEN

POST /v1/vault/add-from-run          (Authorization: Bearer <SCRAPFORAI_API_KEY>)
{ "id": "REG-209", "fromJobId": "job_abc123", "title": "Total ignores discount",
  "type": "BUG", "severity": "HIGH", "surface": "checkout", "ledgerRef": "npdev:REG-209" }

// ... the bug is fixed and deployed ...

POST /v1/vault/REG-209/confirm-green  (Authorization: Bearer <SCRAPFORAI_API_KEY>)
{ "buildId": "2026.11.3-rc1" }
  1. add-from-run takes a run that failed, saves its steps as a library routine (credentials stripped), pins the run as provenRed and creates the item.
  2. confirm-green runs the same routine version. Only if it passes is the run pinned as firstGreen. If it is still red the answer is 409 and the item is untouched.
  3. POST /v1/vault/:id/run re-checks an item at any time and records lastRun.

Both capture endpoints need the bearer token; a web-console session cannot call them. buildId is stored in the results and in the evidence references so you can say which build was red and which was green. The same is available from the command line:

npm run cli -- vault list --status ACTIVE --tags checkout
npm run cli -- vault show REG-209
npm run cli -- vault run REG-209 --build-id 2026.11.3-rc1
npm run cli -- vault confirm-green REG-209 --build-id 2026.11.3-rc1
npm run cli -- vault export                    # deterministic snapshot of the whole vault

MCP tools: vault_list, vault_show, vault_add_from_run, vault_confirm_green and vault_run.

Running the vault, ordered by impact

A suite item can pull vault items by filter instead of naming routines. With "order": "impact" the items most likely to break after a change run first, so a red run (and failFast) comes early.

POST /v1/suites
{
  "name": "pre-merge",
  "buildId": "2026.11.3-rc1",
  "items": [ { "vault": { "status": ["ACTIVE"], "tags": ["checkout"] } } ],
  "order": "impact",
  "impact": { "changedFiles": ["src/cart/total.js", "web/checkout/payment.html"] },
  "failFast": true
}

The order is: surface touched (an explicit impact.surfaces entry, or a changed file matching the surfaces globs of the target profile) > failed in its last 5 runs > severity > id. Every run records the reasons for its position. POST /v1/vault/plan shows the order and reasons without running anything.

git diff --name-only main > changed.txt
npm run cli -- vault run --impact --changed-files changed.txt --fail-fast --build-id 2026.11.3-rc1

PowerShell: do not pipe into npm run cli -- ...; npm drops the flags when it receives piped input. Write the list to a file (as above) or use scriptsopsInvoke-VaultPreMerge.ps1, which does it for you and uses <branch>.<sha> as the build id. Invoke-VaultNightly.ps1 and Register-VaultNightlyTask.ps1 in the same folder run the vault every night.

It uses the same verdict and exit codes as any suite: 0 green, 1 red, 2 infrastructure error.

The Vault screen

With the web console enabled, Vault lists the items with status, severity, links to the RED and GREEN proof, last run and a per-item Run button. Run by impact takes a list of changed files, shows the order and the reasons, runs the vault as a suite and opens its report. The console authenticates with a session cookie, so capturing evidence (add-from-run, confirm-green), pinning and credentials stay available only through the bearer token, from the API, the CLI or MCP.

Signed evidence

Every pinned run has a manifest.json listing the sha256 of each file. At pin time that manifest is signed with the installation's Ed25519 key (<dataDir>/signing/ed25519.key, readable only by its owner). The keyId is the sha256 of the public key.

  • GET /v1/evidence/public-key returns the public key and its keyId.
  • Evidence pinned before signing existed is listed as unsigned, is not trusted and cannot be exported. Pin it again from a new run.

The chain

Each signed manifest carries chain: { sequence, previousManifestSha256 }. Editing one manifest breaks the next link; removing one leaves a gap in the sequence; removing the most recent ones is caught by a high-water mark (pinned/chain.json).

GET /v1/evidence/chain            // links, gaps, signatures
GET /v1/evidence/chain?deep=1     // also re-hashes every pinned file
npm run cli -- evidence chain --deep

Export and offline verification

npm run cli -- evidence export job_abc123 --out REG-209-red.zip
# on any machine, no server and no configuration:
scrapforai evidence verify .\REG-209-red --expected-key-id <keyId>

GET /v1/runs/:jobId/export (pinned runs only) returns a .zip with the evidence files, the signed manifest, public-key.pem and a README. It is refused (409) if the run is not pinned, has no valid signature from this installation, or its files no longer match the manifest. evidence verify accepts an unzipped folder or a job id; it exits 0 when everything verifies and 1 otherwise. The verification code imports no server configuration on purpose, so it works wherever the files are.

Pass --expected-key-id with the id you obtained from the owner through another channel. Without it, the key inside the folder only proves that the bundle is consistent with itself.

What a signature proves

  • It proves integrity and origin: this installation signed exactly these files, and none has changed since.
  • It does not prove that the test was correct, that the application under test is what it claims to be, or anything about a machine whose private key or whole data directory is compromised.
  • Back up <dataDir>/signing/ and pinned/ together. Pinned evidence is never deleted automatically (the cap is PINNED_EVIDENCE_MAX_MB; over it, a pin is refused with 409).

Reports

A report turns a run, or a whole suite, into a homologation document: application, environment, build, date, executor, routine and version, verdict, steps with times, the failure screenshot, a console and network summary, a teardown warning if cleanup failed, and a footer with the signing keyId, manifest sha256 and chain position (or an explicit "not signed / expired").

GET /v1/runs/job_abc123/report?format=pdf&lang=en
GET /v1/suites/suite_xyz/report?format=html&lang=pt
npm run cli -- report job_abc123 --out report.pdf --format pdf --lang en
npm run cli -- report suite_xyz --out suite.html --lang es
  • format is html (default) or pdf; lang is en (default), pt or es.
  • The HTML is one self-contained file with the screenshots embedded, under a content security policy without scripts. Everything that came from the run is escaped, so the page under test cannot inject anything into it.
  • The PDF is printed by the same Chromium with every network request aborted.
  • A report needs the run's evidence to still exist. Pin what you will report on. A suite report is refused (409) while the suite is still running.
