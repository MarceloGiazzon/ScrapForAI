Credentials, routines & suites

The server-side building blocks that turn one-off runs into reusable, repeatable proof: a credential vault, target profiles, versioned routines, suites, pinned evidence and a command-line client.

Credential vault

Secrets are stored encrypted on the server (AES-256-GCM) and referenced by id. A caller, including an AI model, passes credentialSet: "gam-admin"; the server loads the values and steps keep using valueFromCredential by field name. Values are write-only: no API, log, result or history entry returns them.

PUT /v1/credentials/gam-admin        (Authorization: Bearer <SCRAPFORAI_API_KEY>)
{
  "boundOrigins": ["https://dev.example.com"],
  "values": { "loginUser": "...", "loginPassword": "..." },
  "tags": ["role:admin"]
}
POST /v1/explorations/run
{
  "targetProfile": "app-dev",
  "credentialSet": "gam-admin",
  "steps": [
    { "action": "goto", "url": "$targetUrl" },
    { "action": "fill", "selector": "#vUSER", "valueFromCredential": "loginUser" },
    { "action": "fill", "selector": "#vPASS", "valueFromCredential": "loginPassword" }
  ]
}
  • Origin binding. Each set lists boundOrigins. A fill of a vault value on any other origin fails with CredentialOriginMismatch, even if that origin is allowlisted.
  • Who can write. POST/PUT/DELETE /v1/credentials/:id need the bearer token; a web-console session is not enough. GET returns only ids, origins, field names, tags and last use.
  • Key. SCRAPFORAI_VAULT_KEY (32 bytes, base64) or a generated vault.key in the data directory. Lose the key and the vault cannot be read.
  • MCP. The run_exploration tool has no credentials field, so a model never writes or sees a secret. list_credential_sets shows what exists.
  • Legacy. The REST API still accepts inline credentials (deprecated, logged). Set ALLOW_INLINE_CREDENTIALS=false to require the vault.

Target profiles

A profile names an application and environment, supplies the default targetUrl and lists the credential sets a run may use. It can never widen ALLOWED_TARGET_ORIGINS: a baseUrl outside it is refused.

PUT /v1/targets/app-dev
{
  "name": "My app (dev)",
  "environment": "dev",
  "baseUrl": "https://dev.example.com/app",
  "platform": "genexus",
  "credentialSets": ["gam-admin", "gam-readonly"],
  "flags": { "maxSessionsPerCredential": 1 }
}

Use it with "targetProfile": "app-dev" in a run. maxSessionsPerCredential (default 1) is how many simultaneous sessions one credential may have.

Saved routines

A routine is data, so it can be stored, versioned and reviewed. Every change is a new immutable version (v1.json, v2.json); saving identical content creates nothing. The sha256 of each version is checked whenever it is read.

PUT /v1/routines/crud-sales
{ "title": "Sales CRUD", "targetProfile": "app-dev", "credentialSet": "gam-admin",
  "steps": [ { "id": "auth", "action": "include", "routineId": "login", "version": 1 },
             { "id": "open", "action": "click", "selector": "#menu-sales" } ],
  "teardown": [ { "id": "bye", "action": "goto", "url": "https://dev.example.com/app/logout" } ] }

PUT /v1/routines/crud-sales      { "fromJobId": "job_abc123" }      // save a run that worked
POST /v1/routines/crud-sales/run?version=2
  • Secrets are refused. A literal equal to a vault value, or shaped like an API key, JWT or token, is rejected at save time (422).
  • fromJobId saves the steps of a run that passed, while its evidence still exists.
  • Status: draft, active, quarantined, retired. Changing it is a new version. Suites run only active by default.
  • Set ROUTINE_LIBRARY_DIR inside a git repository to review routines in pull requests.

Include and teardown

{ "action": "include", "routineId": "login" } expands another saved routine in place. Expanded step ids are prefixed with the include id (auth.submit). Up to 3 levels; cycles are refused when saving; the included routine must belong to the same target profile and not be retired. Without version the current version is used, so pin it for reproducible proof. The versions actually used are recorded in result.includes.

teardown is a list of steps that always runs after the steps, pass or fail (like finally): your own teardown first, then those of included routines, last included first. Teardown failures are reported in result.teardown and teardownStatus; they never change the run's status and never replace a step failure.

Suites

A suite runs several saved routines, multiplied by credential sets and target profiles. Starting one answers 202 immediately and it runs in the background.

POST /v1/suites                                  -> 202 { "suiteRunId": "suite_..." }
{
  "name": "nightly",
  "items": [ { "routineId": "crud-sales" }, { "routineId": "report-activity" } ],
  "variants": { "credentialSets": ["gam-admin", "gam-readonly"], "targetProfiles": ["app-dev", "app-qa"] },
  "failFast": false
}
GET /v1/suites/suite_...?wait=30                 // blocks up to 55 s until it ends
  • Each run has a readable variantKey, e.g. crud-sales@v2/cred:gam-admin/target:app-qa. Routine versions are pinned when the suite starts.
  • One verdict: green (exit 0), red (1, a run failed) or infra-error (2, a run could not execute, nothing ran, or it was cancelled).
  • One session per credential. Runs that share a credential set never overlap; a direct run needing a busy credential gets 409 CredentialInUse.
  • failFast stops starting new runs at the first red one; the rest are listed as not run. POST /v1/suites/:id/cancel stops the suite.
  • MAX_PARALLEL_JOBS is the shared pool; INTERACTIVE_RESERVED_SLOTS (default 1) are never given to suites.

Retention and pinned evidence

Evidence expires after ARTIFACT_RETENTION_HOURS (4 h) unless the run uses options.retention: "standard" (STANDARD_RETENTION_DAYS, 30 days). To keep proof for good, pin it:

POST /v1/runs/job_abc123/pin
{ "reason": "proof for REG-209", "ref": "npdev:REG-209" }

GET /v1/runs/job_abc123/manifest   // sha256 of every file, re-verified now

Pinning moves the run to a store that is never pruned (capped by PINNED_EVIDENCE_MAX_MB; over the cap you get 409 and nothing is deleted), drops the heavy trace unless keepTrace, and refuses evidence whose manifest no longer matches its files. The manifest proves the files are unchanged; it does not prove the test was right.

The scrapforai command line

npm run cli -- run crud-sales --version 2 --json
npm run cli -- suite nightly.json
npm run cli -- routines list
npm run cli -- runs show job_abc123
npm run cli -- pin job_abc123 --reason "proof" --ref npdev:REG-209

The CLI talks to the REST API with the key from .env (never from the command line). Exit codes: 0 passed, 1 a test failed, 2 anything else (API down, bad arguments, a run that could not execute). With --json it prints exactly one JSON object on stdout, versioned by cliSchema; progress goes to stderr.

{ "cliSchema": 1, "command": "run", "exitCode": 1,
  "result": { "jobId": "job_...", "status": "failed", "failedStepIndex": 2, "error": { "type": "StepExecutionError", "message": "..." } } }

MCP tools

The recommended flow for an AI agent: list_targets → inspect_dom → run_exploration → save_routine (with fromJobId) → later run_routine or run_suite + get_suite_result.

ToolPurpose
list_credential_sets, list_targetsDiscover what the server offers (never secret values).
inspect_dom, run_explorationExplore a page and run steps.
list_routines, get_routine, save_routine, run_routineThe routine library.
run_suite, get_suite_resultStart a suite (returns at once) and wait for it with waitSeconds.
get_runSummary (and optionally the full result) of a past run.
